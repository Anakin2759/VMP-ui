# VMP-ui 设计目标

> 更新日期：2026-10-08  
> 文档性质：项目级目标与设计约束，用于指导方案评审、实现取舍和验收。  
> 状态说明：本文描述目标状态，不代表相关能力已经实现或通过验证；实际进度以代码、专项规划和测试结果为准。

## 1. 总体目标

构建一个基于 ECS 的轻量级、可嵌入、可测试的 UI 框架，以明确的生命周期和单线程调度为基础，提供成熟的控件交互体验与声明式布局能力。

框架应实现以下核心目标：

1. **核心精简**：仅承担界面运行所必需的实体、输入、布局、调度和渲染职责。
2. **边界清晰**：业务逻辑和通用基础设施由宿主应用负责，可选能力通过明确接口接入。
3. **内部单线程、外部多线程接入**：UI 状态在所属 UI 线程统一访问，外部线程通过受控入口提交请求。
4. **组合式扩展**：通过组件、System 和 Renderer 组合构建控件，避免庞大的继承体系。
5. **可诊断、可验证**：失败有明确结果，关键机制可以脱离真实窗口进行测试。

“轻量级”首先指职责和依赖受控，不等于取消必要功能。构建时间、内存、产物体积和帧耗时的具体指标，应在建立基线后由专项规划确定。

## 2. 职责边界与非目标

### 2.1 UI 库内职责

- UI 实体、组件、层级及其生命周期管理。
- 原生窗口和输入接入、焦点与交互状态管理。
- 布局、主题样式、UI 动画及渲染调度。
- 界面所需的字体、图像及 GPU 资源管理。
- UI 任务投递、唤醒、关闭及结果反馈。
- 必要的错误与诊断信息生成。

### 2.2 宿主应用或独立模块职责

- 业务规则、网络通信、数据库和应用级持久化。
- 通用线程池、后台任务调度及长耗时计算。
- 日志落盘、轮转、远程采集等输出策略。
- 非 UI 专属的资源获取和处理流程；完成后通过受控入口提交结果。

UI 库可以调用应用回调、消费外部结果，但不因此取得业务系统或后台任务的所有权。接口必须说明依赖的所有权、生命周期和线程要求。

### 2.3 非目标

- 不提供与 Qt 完全兼容的 API、对象模型或全部功能。
- 不允许任意线程直接操作 UI Registry，也不为此引入全局 ECS 锁。
- 不建设通用应用框架、通用插件平台或后台任务平台。
- 不把可选功能及其第三方依赖变成 UI 核心的强制依赖。
- 不为实现本文目标直接重写已经稳定的模块；变更须有实际缺口和验证依据。

## 3. 功能与架构目标

### G1：建立明确的 ECS 状态与生命周期模型

**目标要求**

- 内部使用 EnTT 管理实体；公共接口不暴露 EnTT 类型或其他内部第三方实现细节。
- 组件保存几何、层级、交互、样式、事件回调及布局关系等数据，复杂行为由 System 执行。
- Runtime、Registry、System 和渲染资源的所有权、创建顺序及销毁顺序明确。
- 对无效实体、已销毁目标和跨 Runtime 误用提供可诊断结果。
- 控件差异优先通过组件和策略表达，而不是层层继承。

**验收标准**

- 生命周期测试覆盖创建、销毁、重复初始化及失效句柄使用。
- 销毁对象后，排队请求和关联关系不得访问已释放状态。
- 公共头自包含检查通过，消费者无需直接接触内部 ECS 实现。

### G2：以单 UI 线程统一调度

**目标要求**

- 每个 Runtime 的可变 UI 状态由明确的所属 UI 线程管理；这不意味着默认承诺多 UI 线程或多 Runtime 并行支持。
- 事件循环接收原生事件与排队请求，并按明确阶段处理输入、应用回调、动画、布局和渲染。
- 应用回调不得长期阻塞 UI 线程；长耗时工作交由库外执行。
- 明确任务顺序、回调重入、帧调度、唤醒和异常处理规则。
- 关闭过程必须规定何时停止接收任务，以及如何处理已接收但未执行的任务。

**验收标准**

- 通过测试验证线程归属、阶段顺序、唤醒、重入和关闭行为。
- 队列中任务执行失败不得无提示地破坏后续调度。
- 正常 UI 状态访问不依赖全局 Registry 锁。

### G3：提供受控的跨线程请求入口

**目标要求**

- 采用多生产者、单 UI 消费者的接入模型。
- 外部线程可提交创建、销毁、更新、刷新、重排或退出请求；请求的实际 UI 操作仍在 UI 线程执行。
- 跨线程业务事件只能通过明确支持排队的入口提交，不等于允许任意线程直接触发内部事件分发器。
- 投递入口具有明确的容量和背压策略，区分“成功入队”与“执行完成”。
- 队列满、Runtime 已关闭、执行时目标失效及任务执行失败均有可观察的处理结果。
- 跨线程传递任务、命令或具有明确所有权的数据，不携带无生命周期保障的引用。
- 状态查询优先使用不可变快照或排队请求/响应；如提供阻塞查询，必须定义超时、关闭与防死锁规则。

**禁止行为**

- 工作线程直接读写 UI Registry、布局或交互状态。
- 工作线程直接调用内部 Renderer 或 GPU 资源接口。
- 在任意线程执行约定只能在 UI 线程运行的回调。

**验收标准**

- 覆盖多生产者并发、队列满、投递与关闭竞争、目标先销毁后执行等场景。
- 成功接收的请求按约定执行或取消，不无故丢失、不重复执行。
- 使用者可区分投递失败与执行失败。

### G4：提供可组合、可诊断的布局能力

**目标要求**

- 支持类似 Qt Quick anchors 的边锚点、中心锚点、`fill`、`centerIn`、边距和偏移量。
- 支持最小、首选和最大尺寸约束。
- 明确锚点目标的合法范围、坐标空间和窗口归属限制。
- 定义 `fill`、`centerIn` 与显式锚点的互斥或优先级规则，检测过约束和循环依赖。
- 目标销毁时使关系安全失效，并按约定报告或恢复布局。
- 锚点与 Flexbox 等布局策略互补，明确同一几何属性的控制权，避免互相覆盖。
- 增量更新覆盖所有受影响的依赖对象，不仅限于父子子树。

布局处理应形成可验证的数据流：约束收集 → 依赖检查 → 几何求解 → 尺寸约束处理 → 更新布局结果 → 通知命中测试和渲染。实际阶段拆分由专项设计确定。

**验收标准**

- 无真实窗口时可测试基础锚点、尺寸约束、冲突、循环及目标销毁。
- 求解失败具有确定的恢复或保留策略，不输出 NaN、无穷值或未定义几何结果。
- 验证锚点与容器布局共存，以及脏标记对依赖对象的传播。

### G5：提供组合式控件与一致的交互体验

**目标要求**

- 借鉴 Qt 的成熟交互语义，但保持 VMP-ui 自身的 ECS、生命周期及声明式构建模型。
- 基础能力覆盖窗口、对话框、按钮、文本显示和编辑、选择控件、滑块及进度条。
- 逐步覆盖弹出层、滚动容器、列表、表格、菜单、工具栏和状态栏。
- 控件由数据组件、交互状态、布局、样式、Renderer 和 System 组合构成。
- 焦点、禁用、可见性、鼠标、键盘及文本输入行为保持一致。
- 主题和动画属于 UI 能力，但不应强制引入无关的应用级服务。

上述控件名称描述能力范围，不强制公共 API 必须与 Qt 同名。

**验收标准**

- 基础控件具备状态机单元测试与输入交互测试。
- 示例可通过公共 API 组合常见窗口和对话框，不依赖内部 Registry 或第三方头文件。
- 控件销毁、隐藏、禁用及焦点切换不会遗留无效交互状态。

### G6：保持渲染与更新成本可控

**目标要求**

- 布局、命中测试和渲染通过脏标记协调更新，避免无变化时重复执行全量工作。
- 渲染后端与控件逻辑解耦，能力不足或初始化失败具有明确的错误或降级语义。
- 渲染资源的创建、使用和释放遵循所属线程及设备生命周期契约。
- 优化必须建立在正确性与可重复测量之上，不以不安全的状态缓存换取性能。

**验收标准**

- 测试覆盖脏标记传播、窗口尺寸变化、资源失效及后端降级。
- 通过计数或基准测试验证无变化与局部变化场景的工作范围。
- 通过渲染回归验证优化不改变预期显示结果；具体性能阈值另行制定。

### G7：保留诊断能力，剥离通用输出策略

**目标要求**

- 无效实体、布局失败、投递失败、资源失败及生命周期错误具有明确结果或诊断记录。
- 可恢复操作优先沿用项目统一的 `Result<T>` 契约；日志不替代错误返回。
- UI 库负责产生必要诊断，日志文件、轮转与远程采集由应用或独立模块负责。
- 诊断接口明确回调线程、消息有效期、异常与重入约束。
- 可选诊断输出不可成为 UI 初始化成功的前置条件。

**验收标准**

- 未配置文件输出或外部日志库时，UI 核心仍可正常运行。
- 错误路径可通过返回值或测试捕获接口验证，无需解析磁盘日志。
- 输出失败不覆盖业务错误、不引入悬空访问或递归日志。

该目标已按策略 A 落地：UI 内部默认输出到 `stderr`，不再负责日志文件落盘和轮转；宿主通过 Logger 回调接管文件或远程输出。旧日志路径配置仅作为兼容字段保存并提示废弃，不代表内部仍会创建日志文件。详细迁移记录见 [spdlog 移除与轻量日志迁移规划](../todo/SPDLOG_REMOVAL_PLAN.md)。

## 4. 共性质量约束

| 维度 | 设计约束 | 验证方式 |
| --- | --- | --- |
| 简单性 | 不为假设中的扩展引入通用框架 | 评审新增抽象是否解决真实需求 |
| 解耦 | 依赖显式传递，边界接口稳定，可选服务可替换 | 架构门禁、替代实现测试 |
| 安全性 | 生命周期、线程归属和失败语义明确 | 异常路径、并发投递与销毁测试 |
| 可测试性 | 纯逻辑与平台窗口/GPU 依赖分离 | 无窗口单元测试加平台集成测试 |
| 可发行性 | 公共头不暴露内部第三方依赖 | 公共头检查、安装消费者构建 |
| 可观测性 | 正常路径与失败路径均有可验证结果 | 返回值、诊断捕获及更新计数 |

## 5. 优先级与推进原则

| 优先级 | 目标 | 推进条件 |
| --- | --- | --- |
| P0：基础契约 | G1、G2、G3 的生命周期、线程和关闭协议 | 先验证现有实现，修复已确认缺口 |
| P1：基础界面闭环 | G4 基础布局、G5 基础控件、G6 渲染正确性 | 建立输入到布局再到显示的完整验证链 |
| P2：体验与扩展 | 高级控件、主题动画完善、复杂列表与布局 | 不破坏已有线程与生命周期契约 |
| 持续约束 | G7 及共性质量约束 | 贯穿所有阶段，不延后错误处理和可测试性 |

Grid、通用复杂约束及更高级的 Qt Quick 风格能力属于后续扩展方向，不作为基础版本的完成门槛。

优先级不是当前实现进度或强制重写顺序。每项工作开始前应确认“已实现、部分实现、缺失”状态，并据此制定具体变更范围。

## 6. 目标验收与文档维护

每个目标的实施记录应至少包含：

1. 关联目标编号及本次覆盖范围。
2. 实际代码位置和与目标之间的差距。
3. 接口、兼容行为及生命周期影响。
4. 测试用例、执行环境和实际结果。
5. 未覆盖场景、限制及后续工作。

只有具备实现和验证证据的范围才能标记为完成；未运行的测试或未支持的平台不得视为通过。具体接口、算法、迁移步骤和工期放入专项规划，本文保持项目级目标的稳定性。
